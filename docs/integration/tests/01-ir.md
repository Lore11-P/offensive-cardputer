## Findings

### IR-01 — P0 (rischio OOM/reset) — Picco di memoria non sostenibile sui file `.ir` grandi

**File:** `src/modules/ir/IrMenu.cpp:587-590` (`std::istringstream stream(text)`),
`:771-789` (`openFile`), `:496-514` (`parseRawValues`), `:485-494` (limiti).
**Severità:** P0 potenziale: crash/abort su file presenti nel dataset; da
misurare con heap reale prima di dichiararlo P0 definitivo.

Il flusso di `openFile()` è:

1. `storage::fileSize(path) > kMaxIrFileBytes` (64 KB) → altrimenti continua.
2. `std::string text; storage::readText(...)`: per un file >32 KB la `std::string`
   cresce per raddoppio e arriva a **capacity 65.536 B**, anche se il file è
   51–61 KB.
3. `parseIrFile(text)`: il costruttore `std::istringstream stream(text)` **copia
   tutta la stringa** nel buffer dello stream (altri ~51–61 KB).
4. Il parser alloca `commands` (100 × `IrCommand`, ~8 KB) e, per ogni comando
   raw, `rawData.reserve(128)` poi crescita 256→512: **fino a 1 KB di capacità
   per comando** (`512 × uint16_t`), anche se i valori reali sono meno.
5. Solo alla fine `text` viene liberato; durante il parsing testo + copia +
   vettori + menu padre sono tutti vivi.

Stime sui file reali (testo 64 KB + copia + raw + struct):

| File | Dimensione | Comandi | Picco stimato |
|---|---:|---:|---:|
| `Proiettori/NEC/NEC_RU_M124.ir` | 60.922 B | 53 | ~180 KB |
| `DVD/JVC/JVC_HR-J700E.ir` | 52.840 B | 40 | ~165 KB |
| `Clima/Hisense/Hisense_DG11J1-99_celsius.ir` | 51.298 B | 35 | ~155 KB |
| `Clima/Fujitsu/AC_ASU18RLF.ir` | 49.437 B | 44 | ~155 KB |
| `Clima/Daikin/Daikin_FTX50GV1B.ir` | 39.226 B | 4 | ~110 KB |

La RAM statica finale è 115–128 KB su 327,7 KB; il framebuffer è allocato a
runtime (~64,8 KB). Restano ~135 KB contendibili, meno menu e driver SD: i primi
quattro file sono sopra o al limite. `std::bad_alloc`/abort non è gestito.

**Fix suggerito:** eliminare la copia dello stream (parser a indice su
`std::string_view` o lettura a righe dal `File` con buffer fisso); imporre un
budget totale di valori raw per file (es. 8.000–10.000 `uint16_t`) e una
capacity massima per comando; aggiungere un gate `ESP.getFreeHeap()` prima di
leggere file >32 KB e un messaggio esplicito se il file non entra. In
alternativa abbassare `kMaxIrFileBytes` a una soglia misurata e dichiararla.

### IR-02 — P1 — Raw >512 valori troncato e trasmesso come frame valido

**File:** `src/modules/ir/IrMenu.cpp:489-514` (`kMaxRawValues` e
`parseRawValues`), `:576-580` (`finalizeCommand`), `:756-765` (`sendCommand`).
**Severità:** P1: funzione rotta per i climatizzatori/ventilatori con frame lunghi.

`parseRawValues` si ferma a 512 valori, ma `finalizeCommand` imposta
`supported = !command.rawData.empty()` senza sapere se il frame è stato
troncato. `sendCommand` invia i 512 valori, l'apertura da menu non segnala
l'errore e i tasti rapidi mostrano "Inviato"; lo scanner invia lo stesso frame
troncato. La soglia non è un limite teorico: la scansione del dataset trova
**42 file e 129 comandi** con `data:` >512; 23 file sono in `Clima`:

- `Clima/Daikin/Daikin_FTX50GV1B.ir`: Power 585 valori → 512 (manca la coda,
  compreso il checksum);
- `Clima/Honeywell/Honeywell_Fan_HY041w.ir`: Power 959 → 512;
- `Clima/Aldi/Easy_Home_Portable_Air_Cooler.ir`: 863 → 512;
- `Clima/Dyson/Dyson_PurifiyHumidify_PH04.ir`: 795 → 512;
- `Proiettori/Epson/Epson_EB-E20.ir`: 951 → 512.

Il REPORT dice solo "massimo 512 valori" e non dichiara il troncamento; `SOURCES.txt`
dice addirittura che i tempi raw sono preservati. Inoltre il REPORT afferma che
i climatizzatori usano solo NEC/NECext: la scansione dei protocolli non vede i
file raw (non hanno `protocol:`), quindi i 23 file Clima con raw >512 non sono
contati. Questo è il caso P03 della review QA: mai inviare un frame troncato
spacciandolo per valido.

**Fix suggerito:** aggiungere `bool truncated` a `IrCommand`; se il `data:` ha
altri token dopo il 512°, marcare il comando `[n/d]` con messaggio "Frame troppo
lungo (N valori, max 512)" e non trasmettere. In alternativa alzare il limite a
1.024 con un budget di memoria per file e una stima del picco.

### IR-03 — P1 — Perdita dei preferiti su SD quando la SD manca

**File:** `src/modules/ir/IrMenu.cpp:306-326`, purge a `:314-319`; filtro di
visualizzazione a `:1077-1090`.
**Severità:** P1: corruzione di dati persistiti (NVS), non recuperabile.

`toggleFavorite` elimina dalla lista tutti i path per cui
`storage::exists(p)` è falso, e poi salva. Con la SD assente (o non montata al
boot), i preferiti aggiunti dall'albero SD (`/ir/TV/...`, `/ir/Clima/...`) non
esistono per `storage::exists` e vengono cancellati al primo `F`, anche se la SD
tornerà. In pratica: 20 preferiti su SD + avvio senza SD + aggiunta di un
telecomando LittleFS = 20 preferiti persi. `runFavorites` intanto mostra "Nessun
preferito salvato", non "SD assente", quindi l'utente non capisce cosa è
successo.

**Fix suggerito:** non eliminare un path se il backend che lo contiene non è
disponibile. Il caso semplice: eseguire la pulizia solo se `storage::hasSD()`
oppure solo per path che non dipendono dalla SD; meglio memorizzare il backend
(`SD`/`LittleFS`) insieme al path, oppure non pulire mai in `toggleFavorite` e
limitarsi a nascondere le voci non risolvibili in `runFavorites`.

### IR-04 — P1 — SIRC20: extended address a 8 bit perso

**File:** `src/modules/ir/IrMenu.cpp:540-543` (bits=20), `:689-694`
(`encodeSony(bits, command, address)`); libreria:
`IRsend.h:318-319` (`extended = 0`), `ir_Sony.cpp:89-107`.
**Severità:** P1: 1.062 comandi SIRC20 non funzionanti.

Flipper-IRDB rappresenta SIRC20 con address a 13 bit (5 bit device + 8 bit
extended; encoder Flipper: `(*data >> 7) & 0x1FFF`). Il wrapper passa l'address
completo come terzo argomento di `encodeSony`, che per 20 bit usa solo
`address & 0x1F` e riceve `extended = 0` di default. Esempio reale:
`LG/LG_MR21GC_Magic_Remote.ir` address `10 01 00 00` → 0x0110; il codice invia
device 0x10 + extended 0 invece di 0x10 + 0x08. Stesso problema per Samsung
hospitality (`5A 0E`) e Sony SFRTV5.

**Fix suggerito:**

```cpp
const uint16_t device = static_cast<uint16_t>(address & 0x1F);
const uint16_t extended = static_cast<uint16_t>((address >> 5) & 0xFF);
const uint32_t data = g_sender.encodeSony(bits, command & 0xFFFF, device, extended);
```

Per SIRC12/15 il comportamento attuale va bene; la correzione va applicata solo
al ramo `bits == 20`.

### IR-05 — P1 — Ricerca: il cap di 40 è consumato dalla prima marca/categoria

**File:** `src/modules/ir/IrMenu.cpp:1153` (`kMaxResults = 40`),
`:1158-1187` (loop), `:1170` (titolo senza categoria).
**Severità:** P1: ricerca per marca parzialmente rotta; F09 e test REPORT #4.

`brandHit` è true se il nome della marca contiene il testo cercato; in quel caso
vengono aggiunti **tutti** i file della marca, categoria per categoria
nell'ordine TV→Clima→Audio→… Con "samsung" la TV ha 57 file: i primi 40
riempiono il cap e Clima (3), Audio (13), DVD (6) e Proiettori (3) non vengono

Proiettori e Altro.

Inoltre il titolo è `marca / modello` senza categoria: i duplicati dello stesso
telecomando in categorie diverse sono indistinguibili (vedi IR-07).

**Fix suggerito:** includere la categoria nel titolo (`TV · Samsung / ...`),
distribuire il cap tra categorie (round-robin) o applicare un cap per marca;
in alternativa mettere prima le corrispondenze sul modello e poi quelle sulla
marca, oppure deduplicare per `(marca, modello)` prima del cap.

### IR-06 — P2 — Categorie e marche senza file `.ir` restano visibili (F05/C01/C02)

**File:** `src/modules/ir/IrMenu.cpp:1116-1137` (`runRemotes`),
`:1100-1114` (`runCategory`), `:865-871` (`openBrand`), `:182-204`
(`categoryBrands`).
**Severità:** P2: viola F05/C01/C02; nessun crash.

`runRemotes` decide se mostrare una categoria guardando solo se
`categoryBrands(category)` è vuoto. `categoryBrands` elenca le **directory**,
non i file: `/ir/Clima/Brand` vuota (o con soli file non `.ir`) fa comparire
`Clima`, e aprendola si vede "Nessun file .ir per questa marca". Lo stesso vale
per `runScannerBrands`. Con il dataset consegnato non ci sono cartelle vuote,
quindi il difetto si vede solo con fixture, ma il test è esplicitamente P0 nella
review QA.

**Fix suggerito:** filtrare le marche con almeno un file `.ir` prima di
mostrare la categoria; per non scansionare 343 marche a ogni apertura, calcolare
una sola volta per categoria (o memorizzare un indice) e usare la stessa
funzione in `runRemotes`, `runCategory` e `runScannerBrands`.

### IR-10 — P3 — Lo scanner non spiega perché un file viene saltato

**File:** `src/modules/ir/IrMenu.cpp:946-950` (`readText` controllato, nessun
messaggio), `:771-777` (`openFile` mostra il motivo).
**Severità:** P3: nessun invio errato, solo UX incoerente.

`runScanner` usa correttamente il valore di ritorno di `storage::readText` e,
se fallisce (file >64 KB o errore I/O), non chiama `parseIrFile`: la

kMaxIrFileBytes` prima di `readText` e mostrare `feedback = "File troppo
grande"`; se `readText` fallisce, mostrare "File illeggibile" e non presentare
il file come privo di Power.

### IR-11 — P2 — Deduplica case-sensitive in `storage::list` e caso D05

**File:** `src/utils/Storage.cpp:165-166` e `:212-216` (`std::unique` per nome
esatto), `src/modules/ir/IrMenu.cpp:192-198` (confronto lowercase solo per
l'aggiunta del vecchio albero).
**Severità:** P2: fixture D05/N04; con il dataset attuale non si vede.

`storage::list` unisce LittleFS e SD e deduplica per nome **esatto**; su FAT32
il case è irrilevante, su LittleFS no. Se una marca esiste come `Samsung` in
`/ir/TV` e come `samsung` nell'albero piatto, il controllo `known` la considera
già presente e salta il vecchio albero, ma `brandBases` cerca `/ir/Samsung` con
il case della categoria e su LittleFS non lo trova: i file legacy spariscono
invece di essere fusi. Simmetricamente, due directory con case diverso possono
apparire come due marche.

**Fix suggerito:** normalizzare il case nella deduplica di `storage::list`
(almeno per le directory) o deduplicare le marche in `categoryBrands` con una
mappa lowercase e usare il nome reale per aprire i file.

### IR-14 — P2 — Valori raw >65.535 saturati in silenzio

**File:** `src/modules/ir/IrMenu.cpp:508-512` (`std::min<long>(parsed, 65535)`).
**Severità:** P2: può alterare le pause tra frame; non è dichiarato nel REPORT.

La scansione trova **4.740 valori >65.535 in 275 file** (es.
`Altro/Unknown/Light_Strip.ir` 96.457, `Panasonic/VT_series.ir` 73.312,
`Clima/Botti/Botti_BL-168DLR.ir` 96.841). Il tipo `uint16_t` di
`IRsend::sendRaw` impone il tetto, ma la saturazione va dichiarata; se il valore
lungo è una pausa tra frame, accorciarla a 65.535 ms può cambiare il
riconoscimento su alcuni dispositivi. Il caso Inno-Hit (`783799` finale) è
probabilmente innocuo perché è la pausa di coda.

**Fix suggerito:** documentare il limite nel REPORT e nell'help; se serve,
distinguere le pause di coda (sicure da saturare) dai timing interni al frame e
marcare questi ultimi come `[n/d]`.

### IR-15 — P2 — Ricerca lenta e non interrompibile

**File:** `src/modules/ir/IrMenu.cpp:1158-1187`.
**Severità:** P2: H05; l'utente può credere che il dispositivo si sia bloccato.

`listRemotes` per **tutte** le 916 marche, con `storage::exists` per ognuno dei

(cache in RAM di marca → file) e cercare su quello.

### IR-17 — P2 — Scanner globale: categorie invece di marche

### IR-18 — P2 — REPORT non aggiornato alla build integrata

**File:** `src/modules/ir/REPORT.md:89-93`; artefatto
`.pio/build/cardputer-adv-offensive/firmware.bin`.
**Severità:** P2: documentazione/accettazione, non codice.

Il REPORT dichiara `firmware.bin` 2.363.152 byte e flash 2.362.793 byte. Il
binario finale integrato presente nel worktree è **2.618.256 byte** (HEAD
`f19b6d0`), quindi la misura del REPORT non descrive il codice finale. Rispetto
al limite di 2.5 MB usato dalla review QA (2.621.440 B) restano solo **3.184
byte**; rispetto alla partizione reale `0x2B0000` (2.818.048 B) c'è più margine,
ma il dato va riallineato e la crescita IR (+4,6 KB) va misurata sulla build
finale.

**Fix suggerito:** rigenerare il REPORT con la dimensione finale e la baseline
corretta; aggiungere il conteggio IR e la dimensione SD alla build integrata.

### IR-19 — P3 — Piccoli difetti di preferiti/UX

### IR-20 — P2 (documentazione) — Precedenza LittleFS/SD non dichiarata

**File:** `src/utils/Storage.cpp:103-116` (`openRead` preferisce LittleFS),
`src/modules/ir/IrMenu.cpp:231-252` (dedup per nome).
**Severità:** P2: D01/D03 chiedono una scelta deterministica e documentata.

Il comportamento è deterministico (LittleFS prima, poi SD), ma il REPORT non lo
dice. Con lo stesso path presente su entrambi i filesystem si apre sempre
LittleFS; con lo stesso nome in `/ir/TV/<marca>` e `/ir/<marca>` vince il file
della categoria (l'ordine dei base in `brandBases`). Va scritto nel REPORT per
rendere riproducibili i test D01/D03.

**Fix suggerito:** aggiungere al REPORT la precedenza e il criterio di dedup
(`categoria` prima di `legacy`, case-insensitive sul nome file).
